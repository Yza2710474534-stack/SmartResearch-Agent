# 架构与数据流

当前版本是用于验证证据链的固定研究工作流。模型分别承担证据提取和报告写作，Python 程序负责输入、校验、流程分支和产物保存。

## 1. 模块边界

| 模块 | 职责 |
| --- | --- |
| `cli.py` | 读取参数与本地配置，选择 provider，显示阶段进度和错误 |
| `schemas.py`、`sources.py` | Pydantic 数据契约；读取清单、限制资料范围、保存来源与哈希 |
| `providers.py` | 统一生成接口；离线规则摘录及 OpenAI 结构化输出 |
| `validation.py`、`report.py` | 原文摘录与引用校验；渲染可点击的证据和来源链接 |
| `pipeline.py` | 串联各阶段；无证据分支；快照、事件及最终状态保存 |

`Provider` 定义两个操作：`extract(topic, sources)` 和 `write(topic, evidence, gaps)`。现有 `DemoProvider` 与 `OpenAIProvider` 共享输入、校验和导出流程。未来可扩展模型服务或编排方式。

## 2. 核心数据契约

| 对象 | 关键字段 | 说明 |
| --- | --- | --- |
| Source | id、title、path、url、note、content、sha256 | `S1` 等来源编号；正文保留原有空白与换行 |
| Extraction | items、gaps | 模型提出的候选摘录和资料缺口 |
| Evidence | id、source_id、quote、finding、start_line、end_line | `E1` 等证据编号由程序分配，行号在原文中计算 |
| Claim | text、evidence_ids | 每项结论至少关联一个证据编号 |
| Report | title、sections、gaps | 分章节组织结论；保留提取阶段已经发现的缺口 |

模型接收的资料被标注为内容输入，提示词要求不执行资料中的指令。模型输出通过 Pydantic 结构校验，程序随后核对证据来源及摘录；结构正确与事实正确分别处理。

## 3. 校验与失败行为

1. **输入校验**：清单是 UTF-8 JSON；编号唯一；文本文件位于清单目录内；路径、编码和大小符合限制。
2. **证据校验**：来源编号必须存在；摘录必须是对应资料中的连续原文；行号取首次出现的位置。
3. **无证据分支**：提取结果为空时不调用写作模型，生成信息不足说明。
4. **报告校验**：每项结论引用的证据必须存在；正文中的手写 `[E1]`、`[S1]` 引用会被拒绝。
5. **失败记录**：运行目录保留已产生的快照与中间结果；`run.json` 记录失败阶段和简明原因，避免保存原始 API 错误响应中的敏感信息。

摘录存在不等于推论得到支持。当前没有自动完成来源真实性、主题相关性、时效性、数字口径和因果关系核实，`semantic_support_verified` 保持为 `false`。模型没有列出缺口也不代表资料全面。

## 4. 每次运行的文件

| 文件 | 内容 |
| --- | --- |
| `report.md`、`report.json` | 供人阅读或后续程序消费的报告 |
| `extraction.json`、`evidence.json` | 未验证的提取输出和已验证的证据、来源及行号 |
| `sources.json`、`sources/*.txt` | 资料元信息和本次使用的文本快照 |
| `validation.json` | 校验结果及其实际覆盖范围 |
| `run.json`、`events.jsonl` | 运行编号、版本、主题、模式、模型、状态、耗时、用量及阶段事件 |

资料哈希对应保存为 UTF-8 的快照内容；运行输入哈希同时包含资料元信息。资料快照使原文可以复查，真实模型的输出仍可能变化。每次运行使用新的目录，已有报告保留。

## 5. 后续演进

规划、搜索与向量检索可以先产生同样的 `Source` 和 `Evidence`，再接入当前写作与导出流程。Data Analyst 的数值和图表需要单独记录数据来源与计算方法。LangGraph 的共享状态可承载这些结构，并增加有次数限制的补搜和审阅分支。

具体验收目标见[开发路线](roadmap.md)。
